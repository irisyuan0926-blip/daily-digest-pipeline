# 踩坑清单（都是实测过的，别再踩第二遍）

## 一、邮件体积与送达

### 163 邮箱对 >10KB 的 HTML 会静默拦截
- **现象**：16.2KB 那封 `queued: true`、在已发送列表里能查到，**但用户根本没收到**；同批 13.9KB 那封正常送达。
- **排查**：服务端说发出去了 ≠ 用户收到。用户反馈没收到时，**不要争辩，直接拆更小重发**。
- **安全线**：单封 ≤ 10KB。拆封时按段落整块切，不要把单个段落劈开。
- **根治**：改用「摘要 + 网页链接」，邮件稳定在 2.6KB，这个问题彻底消失。

### 体积量级换算（全量邮件模板）
CSS 约 2.5KB + 每条活动约 0.44KB → **10KB ≈ 15–17 条**。据此估算要拆几封。

### 纯换格式救不了体积
55 条实测：HTML(class CSS) 18.0KB、语义化 HTML 零 CSS 15.0KB、Markdown 12.1KB、纯文本 11.7KB —— **全部超过 10KB**。
因为文字内容 7.5KB + URL 3.1KB = **10.6KB 是理论下限**，任何格式都省不掉。内容全进邮件，必然拆封。

### 把超长 HTML 当工具参数输出会整段丢失
- 超过约 20KB 时，连续多次调用都把 params 整个丢了，报错长得很像参数格式错（`required error field_name: to`），**其实是参数根本没生成出来**。
- 教训：遇到「参数莫名丢失」，先怀疑**输出长度**，不是工具坏了。
- 这也是要切「摘要 + 链接」的直接原因：参数只有 2.6KB，不再触发这个问题。

## 二、Agent Mail / 发信工具

### `to` 必须是数组
```
[{"email": "xxx@163.com", "name": "名字"}]
```
写成对象 `{item:{...}}` 或裸字符串，报 `check input schema type error field_name: to schema_type: array field_type: object`。

### `queued: true` 只代表服务端受理
发完必须再用列表接口核对「在已发送列表里」——但这也只能证明发出去了，不能证明收到。

### 报错先跑「真·最小测试」
曾经连着两次误判：第一轮甩锅 MCP server 有 bug，第二轮拿一个本身格式就错的「最小测试」去验证。
**正确姿势**：用一份已知正确的最小参数（比如发给自己一句 `test`）跑一次，能通就是参数问题，不通才是 server 问题。

## 三、网页渲染

### CSS 变量主题：基础样式必须排在主题前面
```
<style>{BASE}\n{THEME}</style>   ✅ 主题覆盖默认值
<style>{THEME}\n{BASE}</style>   ❌ BASE 里的默认 :root 会把主题盖回去
```
同优先级下后者覆盖前者。**改完渲染器务必校验**：正则取出 CSS 中**最后一个** `--hero:` 定义，确认是主题色而不是默认值。

### 邮件客户端只认 inline CSS
网页能用的 flex / grid / sticky / 伪元素，在邮件里大面积失效。所以：
- 网页版：用 class + CSS 变量，可以做筛选、hover、响应式
- 邮件版：关键样式全部 inline，布局用最朴素的 table / div

## 四、采集

### 先测网络可达性，再定信源
别等子代理跑了二十分钟才发现域名根本打不通。每个域名最多试 1 次，失败就标注并放弃。

实测（2026-09-03，某受限网络环境）：
- ❌ 完全不可达：`reddit.com`（含 `.json` / `.rss` / `old.reddit`）、`x.com` / `twitter.com`、`facebook.com`、`news.ycombinator.com`、`r.jina.ai`、`www.google.com`
- ✅ 可达替代：`hn.algolia.com`（HN 官方 Algolia API，拿 HN 数据的唯一通路）、`dev.to/api`（官方 API）、`mp.weixin.qq.com`（单篇公众号文章页，有 URL 就能抓）、`weixin.sogou.com/weixin`（搜狗微信搜索）
- 结论：**先跑一次连通性测试再承诺能拿到什么**，抓不到的如实标缺口。

### 前端渲染的站点抓不到列表
Devpost、Lu.ma 都是前端渲染，直接抓 HTML 拿不到列表。改走搜索引擎快照（`site:xxx.com <关键词>`）或聚合站。

### dev.to API 混着大量技术文章
用 `dev.to/api/articles?tag=hackathon` 取回来的多数是文章不是活动，**必须人工判断**，不要把文章当活动收录。

## 五、流程本身

### 别为了「降低阅读障碍」删内容
用户明确要求：**减少阅读障碍靠清晰表达和分层，不是缩减信息**。做过一版砍到 24 条的精简版，被直接否掉。
正确做法：分段、筛选按钮、徽章、导航、折叠——信息一条不删。

### 每期都记分渠道命中数
`某 API 命中 N 条 / 某站点命中 N 条 / 某某域名阻断未采集`。
连续 3 天零命中的渠道，明确建议下线，不要无限期挂着占位。
